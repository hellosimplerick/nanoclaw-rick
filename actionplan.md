# NanoClaw Linux Mint MVP Roadmap (No-Code-Change Assessment)

## Scope and assumptions
- Evidence-based assessment from current repository code only.
- Goal: first runnable Linux Mint setup for LAN use, SSH-administered, with one channel + one model provider.
- No code behavior changed in this document; this is an implementation roadmap.

## Deliverable 1 — Linux Runtime Assessment

### 1) Current macOS / Apple Container assumptions in code

| File | Function | Exact runtime invocation / assumption | Notes |
|---|---|---|---|
| `src/index.ts` | `ensureContainerSystemRunning()` | `execSync('container system status', ...)` | Hard dependency on Apple `container` CLI for health check. |
| `src/index.ts` | `ensureContainerSystemRunning()` | `execSync('container system start', ...)` | Starts Apple Container VM subsystem explicitly. |
| `src/index.ts` | `ensureContainerSystemRunning()` | `execSync('container ls --format json', ...)` | Enumerates running containers through Apple CLI. |
| `src/index.ts` | `ensureContainerSystemRunning()` | `execSync(\`container stop ${name}\`, ...)` | Stops orphaned containers via Apple CLI. |
| `src/container-runner.ts` | `runContainerAgent()` | `spawn('container', containerArgs, ...)` | Launches agents with Apple `container run ...`. |
| `src/container-runner.ts` | `killOnTimeout()` inside `runContainerAgent()` | `exec(\`container stop ${containerName}\`, ...)` | Graceful stop path is Apple CLI specific. |
| `container/build.sh` | script body | `container build -t ... .` | Build script is Apple CLI-specific today. |
| `container/build.sh` | script body | `... | container run -i ...` (usage output) | Example/testing path tied to Apple runtime. |
| `src/channels/whatsapp.ts` | connection update callback in `connectInternal()` | `exec(\`osascript -e ...\`)` | macOS-only desktop notification command when QR auth is needed. |
| `src/config.ts` | module-level constants | `const HOME_DIR = process.env.HOME || '/Users/user'` | Fallback path is macOS-specific convention. |

Additional Apple-specific mount behavior comments are present (directory mount notes and env var workaround), but these are comments/workarounds, not direct runtime commands.

### 2) Is there an existing Docker support branch in code?

**Partially, but not as an executable runtime branch in app code.**

- Present in codebase:
  - Container image is Docker-compatible by structure (`container/Dockerfile`).
- Not present in app runtime logic:
  - No runtime switch that chooses `docker` vs `container`.
  - No `spawn('docker', ...)` / `execSync('docker ...')` path in `src/index.ts` or `src/container-runner.ts`.

Conclusion: there is **image build infrastructure** for a Linux container, but **no in-process Docker engine implementation path yet**.

### 3) Single runtime strategy for Linux Mint

## Recommended default: **Docker engine**

Why this fits your use-case:
1. Linux Mint target: Docker is standard and stable for local/LAN self-hosting.
2. Keeps current security model (OS-level container isolation + explicit mounts) intact, with minimal conceptual drift.
3. Requires smaller code delta than removing containers and building a full local-process sandbox.
4. Aligns with your need for secure defaults while still allowing future skills/provider additions.

### 4) Smallest surface-area changes to make Linux runtime work

1. Introduce runtime engine abstraction with two command providers (`container`, `docker`) in the current execution path (`src/index.ts` + `src/container-runner.ts`).
2. Replace hardcoded `container ...` invocations with engine-selected command builders.
3. Normalize mount flag generation to Docker-compatible syntax (the current combination of `--mount` and `-v` is close, but should be generated by engine adapter).
4. Update `container/build.sh` to use selected engine or provide a Linux build script wrapper.
5. Remove/guard macOS-only `osascript` calls for Linux runtime (or no-op notifier on non-darwin).
6. Expand env pass-through whitelist for chosen provider (`OPENROUTER_API_KEY` minimum) in `src/container-runner.ts`.

## Deliverable 2 — Minimal First Runnable System (MVP)

## Channel pick: **Telegram** (preferred over Discord for MVP)

Justification for this repo/state:
- The app currently assumes one primary channel object (`whatsapp` variable) and message callbacks are already centralized in `src/index.ts`, so one bot-token adapter is straightforward.
- Telegram bot setup for personal LAN/self-host use is typically simpler than Discord gateway intents + permission setup.
- `Channel` interface already exists and mentions Telegram naming semantics (`prefixAssistantName`).

### A) How it is wired now
- `src/index.ts` instantiates `WhatsAppChannel` directly and wires callbacks for inbound messages and metadata storage.
- It uses that channel for send/typing and group sync hooks.
- `src/channels/whatsapp.ts` implements `Channel` and pushes inbound messages into DB callbacks.

### B) What must be altered (files/modules)
- Add `src/channels/telegram.ts` implementing `Channel`.
- In `src/index.ts`, replace hard binding to `WhatsAppChannel` with channel factory (env-based: `CHANNEL=telegram|whatsapp`).
- Keep DB ingestion contract unchanged (`storeMessage`, `storeChatMetadata`) so scheduler/router remain intact.
- Optionally keep WhatsApp code untouched behind channel selection (no rip-and-replace needed).

## LLM provider pick: **OpenRouter first**, local model second

Justification:
- Fastest route to first runnable output with minimal infra burden.
- Local lightweight models can be added second by swapping a base URL/provider shim once the loop is proven.
- Existing runner currently depends on Claude Agent SDK and whitelists only Anthropic-related env vars for container injection.

### A) How it is wired now
- Agent execution happens in container via `container/agent-runner/src/index.ts` using `query(...)` from `@anthropic-ai/claude-agent-sdk`.
- Host filters and mounts `.env` values into `/workspace/env-dir/env`, currently allowing only `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY`.

### B) What must be altered (files/modules)
- In `src/container-runner.ts`, extend allowed env pass-through to include `OPENROUTER_API_KEY` (+ any required provider base/model vars).
- In `container/agent-runner/src/index.ts`, add provider/model configuration path (likely via env-driven options or SDK-supported settings), keeping query loop intact.
- Do **not** alter IPC protocol; it already supports streaming text results back to host.

## Minimal message loop (MVP)

1. Telegram inbound webhook/long-poll delivers message.
2. Channel adapter converts to `NewMessage` and calls existing `onMessage` callback in `src/index.ts`.
3. Existing queue + `runAgent` path builds prompt and calls `runContainerAgent`.
4. Agent runner emits `result` markers.
5. Existing callback sends text reply back through Telegram adapter.

This reuses current DB, queueing, routing, and container IPC with the smallest incremental replacement.

## SQLite footprint (Linux)

Current expected footprint under repo root:
- `store/messages.db` (main SQLite file)
- Runtime side directories already used by system:
  - `data/` (sessions, ipc, env)
  - `groups/` (group folders/logs)

On Linux Mint, with repo in e.g. `/opt/nanoclaw-rick`, DB path becomes `/opt/nanoclaw-rick/store/messages.db`.

## Deliverable 3 — Safety Defaults (Linux)

## 1) Tool permission policy (safe default)

Recommended default policy:
- **Deny by default** for high-risk tools: `Bash`, `WebSearch`, `WebFetch`, filesystem write tools.
- Allow only minimum for MVP response loop: read-only + mandatory MCP tools.
- Elevate tool access explicitly per group/config (opt-in).

Current enforcement point:
- `container/agent-runner/src/index.ts` in `query({ options })` currently hardcodes broad `allowedTools` and sets `permissionMode: 'bypassPermissions'` with `allowDangerouslySkipPermissions: true`.

Change target:
- Convert these to config-driven tool allowlists with conservative defaults and no bypass by default.

## 2) Filesystem sandbox defaults

Recommended default policy:
- Mount only group workspace read-write (`/workspace/group`).
- Mount shared/global context read-only (`/workspace/global`).
- Keep additional mounts disabled unless explicitly allowed by external allowlist.
- Force non-main groups to read-only additional mounts.
- Disallow path traversal and secret-bearing roots.

Current enforcement points:
- Mount assembly in `buildVolumeMounts()` (`src/container-runner.ts`).
- Additional mount validation (`validateMount`, `validateAdditionalMounts`) in `src/mount-security.ts`.
- External allowlist path outside project (`~/.config/nanoclaw/mount-allowlist.json`) from `src/config.ts` + `src/mount-security.ts`.

## 3) Network access policy

Recommended default policy:
- Block outbound network by default at container runtime.
- Allow explicit endpoint allowlist via config (for MVP: Telegram API + OpenRouter only).
- Keep all other egress denied unless user enables.

Current enforcement status:
- **No endpoint-level egress enforcement found in code**.
- Existing code assumes container runtime networking is available; policy must be added in runtime adapter layer and/or host firewall integration scripts.

Suggested code enforcement insertion points:
- Runtime command builder used by `runContainerAgent()` and startup checks in `src/index.ts`.
- Optional new module (e.g., `src/runtime-network-policy.ts`) invoked before container spawn.
